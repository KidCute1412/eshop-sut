## Partition Derivation

Each entry below states basis/classification, representative rationale, nominal dependencies, and surface.

- `NAME-PRESENCE-V01` / `NAME-PRESENCE-I01`: FR01-R01 creates provided versus not-provided Valid/Invalid classes. `Nguyen Van A` and omitted/empty isolate presence; all other fields stay nominal; UI/API. `NAME-WHITESPACE-A01` is Ambiguous because trimming is unspecified; `"   "` directly probes that gap; UI/API exploratory.
- `EMAIL-PRESENCE-V01` / `EMAIL-PRESENCE-I01`: FR01-R02 creates present versus absent classes. A normal address and omitted/empty email isolate presence; other values remain nominal; UI/API.
- `EMAIL-FORMAT-V01` / `EMAIL-FORMAT-I01`: FR01-R04 creates documented-format versus plainly malformed classes. The representatives avoid disputed edge syntax; uniqueness and other inputs stay nominal; UI/API.
- `EMAIL-UNIQUENESS-V01` / `EMAIL-UNIQUENESS-I01`: FR01-R05 creates unused versus existing identity states. Controlled preconditions—not database inspection—establish state; other inputs stay nominal; UI/API. `EMAIL-CASE-A01` is Ambiguous because normalization/case rules are absent; a case-variant pair exposes the gap without an oracle.
- `PASSWORD-PRESENCE-V01` / `PASSWORD-PRESENCE-I01`: FR01-R03 creates provided versus absent classes. The representatives isolate presence while other inputs stay nominal; UI/API.
- `PASSWORD-LENGTH-V01` / `PASSWORD-LENGTH-I01`: FR01-R06 creates at-least-eight versus shorter classes. `ValidPass1!` is clearly valid and `Ab1!` clearly invalid while retaining all character classes; other fields stay nominal; UI/API. They are representatives, not BVA values.
- `PASSWORD-UPPERCASE-V01` / `PASSWORD-UPPERCASE-I01`: FR01-R07 creates uppercase-present/absent classes. The pair differs in uppercase only; other rules stay nominal; UI/API.
- `PASSWORD-LOWERCASE-V01` / `PASSWORD-LOWERCASE-I01`: FR01-R08 creates lowercase-present/absent classes. The pair isolates lowercase; other rules stay nominal; UI/API.
- `PASSWORD-DIGIT-V01` / `PASSWORD-DIGIT-I01`: FR01-R09 creates digit-present/absent classes. The pair isolates an ASCII digit; other rules stay nominal; UI/API.
- `PASSWORD-SPECIAL-V01` / `PASSWORD-SPECIAL-I01`: FR01-R10 creates documented-special-present versus absent classes. `!` is explicitly listed; the invalid representative has none; other rules stay nominal; UI/API. `PASSWORD-SPECIAL-A01` is Ambiguous because `#` is unlisted and list exhaustiveness is unknown.
- `CONFIRM-PRESENCE-V01` / `CONFIRM-PRESENCE-I01`: FR01-R11 creates confirmation-present versus absent UI classes. Populated versus missing/empty confirmation isolates the rule; Password stays nominal. `CONFIRM-MATCH-V01` / `CONFIRM-MATCH-I01`: FR01-R12 creates equal versus unequal input relations; representatives differ only in confirmation; UI.
- `REGISTRATION-COMPLETE-V01`: FR01-R13 produces the Valid success-output class. A complete nominal form, unused email, and guest actor satisfy dependencies; UI only; no success text is assumed.
- `API-REQUEST-V01`: API02–API04 produce the complete request-shape class. `API-REQUEST-I01`, `I02`, and `I03` combine each API property with FR01-R01–R03 requiredness to isolate missing `name`, `email`, and `password`; remaining properties stay nominal; API only; no error response is inferred.
- `API-SUCCESS-V01`: API05 produces the Valid documented response class. A 200/message/id shape represents it after a valid request; ID is variable; API only.
- `FORM-REQUIRED-MARKER-V01` / `FORM-REQUIRED-MARKER-I01`: SF01 creates marker-present/missing output classes. Full name is used for the invalid representative because its requiredness is explicit; other labels stay nominal; UI.
- `FORM-EMAIL-TYPE-V01` / `FORM-EMAIL-TYPE-I01`: SF02 creates compliant/non-compliant observable control classes; `email` versus `text` isolates type; UI.
- `FORM-PASSWORD-TYPE-V01` / `FORM-PASSWORD-TYPE-I01`: SF03 creates masked-password versus clear/non-password control classes. The observable representatives isolate secrecy/type; UI.

## Coverage Decisions

- Normative coverage includes all 41 Valid/Invalid partitions derived from approved requiredness, format, uniqueness, password-strength, confirmation, request/response, shared-form, actor, rejection, success, and redirect rules.
- The 4 `A01` candidates are excluded from normative coverage: whitespace handling, email case normalization, unlisted special characters, and registration step count lack documented expected classifications.
- Those four candidates may be explored later only with outcomes recorded as observations, not requirements.
- Maximum lengths, exact full-name grammar, Unicode semantics, exact invalid API status/body, duplicate-email response details, confirm-password masking, exact Login URL/timing, and UI success text are intentionally unpartitioned because no approved oracle exists.
- Cross-field/state combinations reserved for Phase 5 include password/confirmation equality, complete valid input plus unused email plus guest actor, each invalid input with all unrelated variables nominal, invalid input plus error placement, and valid UI completion plus Login redirect.
- Phase 5—not this report—will decide which test cases provide partition coverage and how compatible partitions are combined.
- Boundary selection is reserved entirely for Phase 4.
