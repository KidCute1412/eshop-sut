# AI Critique (200–300 words)

The clearest place the AI got something wrong was applying a generically "correct" Playwright pattern without checking it against this specific SUT. It reached for `test.describe.configure({ mode: 'serial' })` on the reasoning "these tests share mutable backend state, so they need serial mode" — true as a diagnosis, wrong as a fix. Serial mode's actual contract is "skip everything after the first failure," which is fine for a login-flow smoke test but catastrophic here, because several tests are *designed* to fail (they assert the spec against a backend with known bugs). The first genuine bug it hit — the coupon percent-formula defect — silently swallowed 22 other tests in the same run. The model didn't notice until the run summary showed "22 did not run," and only then reasoned back to the actual semantics of the feature it had used. A second, related mistake: it copied `reuseExistingServer: !process.env.CI` from the Playwright starter template without checking that this backend drops and reseeds its entire database on boot — reusing a live server across browser runs silently carried mutated state (coupon usage counts, order totals) from one run into the next.

Both failures share a root cause: the model reasoned correctly about *what* the code should do in isolation, but not about how a specific configuration flag's side effects would interact with this SUT's stateful, resettable backend. It caught neither proactively — only by actually running the suite and reading the failure counts, not by reviewing the code before execution.

The principle I'm taking from this: when an AI writes test infrastructure (not just test assertions), the infrastructure's *side effects* need the same "run it and check the numbers" scrutiny as the tests themselves — a config line that looks idiomatic can silently invalidate everything downstream of it.
