## 1. What the first AI draft got wrong

| # | Issue | Where | Why the first draft missed it | Fix applied |
|---|---|---|---|---|
| 1 | `test.describe.configure({ mode: 'serial' })` was used in all three spec files under the assumption that "shared backend state ⇒ use serial mode." Playwright's serial mode silently **skips every remaining test in the block after the first failure**. Since several tests are *designed* to fail (they assert spec-correct behavior against a buggy backend), the very first known-bug assertion (FR09-TC01, the coupon percent-formula bug) skipped 12 other tests in that file, and similarly for FR-03 and FR-13. First full run: 12 passed / 3 failed / **22 not run**. | `playwright.config.js` (global `fullyParallel`/`workers`) + all 3 spec files | The AI conflated two different needs — "tests must run in a fixed order because they share mutable state" and "a failing test should abort the rest." Those are not the same thing in Playwright; `mode: 'serial'` implies the second, which was never intended. This is exactly the kind of framework-semantics gap a model can get wrong even when the individual assertions are correct. | Removed `mode: 'serial'` from all three files; ordering is instead guaranteed by a global `fullyParallel: false` + `workers: 1` in `playwright.config.js`, so the run stays deterministic without the fail-fast side effect. Re-run: **29 passed / 8 failed / 0 skipped**, matching the 8 catalogued known bugs. |
| 2 | `page.getByLabel(...)` locators in the FR-03 UI tests (`ForgotPassword.jsx`) timed out after 30s. | `tests/fr03-forgot-password.spec.js` | The AI assumed a `<label>` immediately followed by an `<input>` is enough for Playwright's accessible-name resolution. It isn't — `getByLabel` requires an explicit `htmlFor`/`id` pairing or the input nested inside the `<label>`; `ForgotPassword.jsx` has neither. The AI wrote the "textbook" Playwright locator without checking the actual DOM structure it was targeting. | Fragile-selector fix: replaced `getByLabel(...)` with structural locators (`page.locator('form input[type="text"]').first()`), since each step of the form only renders one input of that type. Documented in a code comment so a future maintainer knows *why* the less-idiomatic selector was chosen. |
| 3 | The FR-13 UI test that reads the dashboard's revenue card raced the page's own data fetch: it read `innerText` immediately after `toBeVisible()`, before `fetchData()` (an async `axios` call in `App.jsx`) had resolved. First run under the fixed serial config still failed with `Received: 0` — not because the app was slow, but because the assertion read the pre-fetch placeholder value. | `tests/fr13-dashboard.spec.js` | Classic flaky-wait smell: the AI asserted on visibility of a static heading as a stand-in for "the data has loaded," which is only true once, coincidentally, when network timing is fast. This is precisely the "flaky waits" failure mode the assignment brief calls out by name. | Replaced the one-shot `innerText()` read with a self-retrying assertion (`await expect(revenueLocator).not.toHaveText('0 ₫')`) before reading the value, so the test waits for the real, fetched number instead of a hardcoded timeout. |
| 4 | The very first full-suite run reused already-running dev servers across separate `--project=<browser>` invocations (`reuseExistingServer: !process.env.CI` from the original scaffold), so state mutated by the Chromium run (coupon usage counts, delivered-order totals) silently carried into the Firefox run instead of each browser getting the same clean fixture data. | `playwright.config.js` `webServer[]` | The AI copied the standard Playwright starter-template pattern (`reuseExistingServer` in non-CI) without accounting for the fact that *this* SUT resets its entire SQLite DB on every `node server.js` boot — reusing the server defeats that reset and breaks the assumption behind stateful tests like the VIP100 usage-limit case. | Set `reuseExistingServer: false` unconditionally for all three servers (backend, frontend-web, frontend-admin) so every `npx playwright test --project=X` run starts from an identical, freshly-seeded database. |
| 5 | Coupon test data initially conflated "the value the real spec says should come out" with "the value the buggy backend actually returns," which would have made assertions pass against the bug instead of exposing it (e.g. accidentally asserting `final_amount === 5000000` for `SAVE10` instead of the spec-correct `450000`). | `tests/data/fr09-coupon.json` design pass | When a script is generated by walking the *implementation* to "figure out what the test should expect," it naturally tends to encode the implementation's behavior — bugs included — as the oracle. That inverts the point of testing against a specification. | All data-driven expectations in `fr09-coupon.json` and the FR-03/FR-13 specs assert the value the **README spec** (`FR-03`, `FR-09`, `FR-13`, `FR-12`) says should happen, not what the code currently does. Where those diverge, the test is expected to fail and the divergence is the bug report. |

## 2. Newly discovered issues (not in the HW02/HW03 bug backlog)

While writing the FR-09 checkout E2E test (`FR09-TC13`), the suite surfaced two defects that were **not** part of the previously filed GitHub issues (#25–#35, #50–#51):

- **BUG-FR09-006**: `POST /api/checkout` never clears the user's in-memory cart (`userCarts[userId]`) after a successful order — spec (`README.md` FR-08): *"Sau thanh toán thành công, giỏ hàng được xóa."* Confirmed by `GET /api/cart` still returning the pre-checkout item after `/api/checkout` returns 200.
- **BUG-FR09-007**: `POST /api/checkout` trusts a client-supplied `total_amount` and inserts it directly into the `orders` table — spec (`README.md` FR-08): *"Backend phải tự tính lại tổng tiền; không chấp nhận giá trị `total_amount` do client gửi lên."* The endpoint (`backend/server.js:297-309`) never recomputes the total from the cart/coupon server-side.

These are logged here for the record; whether to file new GitHub issues for them (in addition to reusing #25–#35/#50–#51 for the already-known bugs) is a decision left to you — see `../02_bug_reports/`.

## 3. Test cases the AI could not (or should not) automate

- **FR03-TC04 (malformed email, no format validation)** — the backend has no server-side email-format check at all, so this case is really "documents current behavior," not a meaningful pass/fail spec check; kept as a single data-driven row rather than a dedicated scenario to avoid inflating the count with a non-assertion.
- **Mobile OTP flow (FR-03M in the HW02/HW03 backlog)** — out of scope for HW04 by the assignment's own instructions ("Pool D mobile is not used in this homework"), so it was intentionally not re-automated here even though it appears in the existing GitHub issue backlog (#50).
- **Email delivery itself** — FR-03 spec says the OTP is sent via email; the demo environment shows it directly in the API/UI response instead, so there is nothing to automate against a real mailbox (this is explicitly called out as demo-environment behavior in the README, not a gap).
