# AI Critique

AI accelerated the initial design of the GUI checklist by organizing candidate checks across visual standards, forms, navigation, and feedback states. It was also useful for normalizing terminology, identifying repeated items, and suggesting a traceable report structure. However, its first-pass output was broader than the evidence supported. Some proposed findings were based on static source inspection or common interface heuristics rather than an observed execution of the EShop interface. This distinction matters because suspicious code does not, by itself, establish a user-visible defect. AI also tended to describe conventional accessibility concerns confidently while overlooking context-dependent behavior, such as the precise order-state rules, recovery paths, and differences that appear only on a real browser or physical device.

These limitations arose from incomplete runtime context and from prompts that initially emphasized coverage more than evidentiary thresholds. A language model predicts plausible patterns; it does not independently establish participant identity, consent, human frustration, device rendering, GitHub activity, or successful task completion. For that reason, AI-generated checklist items and draft findings required human review against the specification, the implemented interface, and authentic execution evidence. Unsupported statements were retained only as test hypotheses or were marked as not executed.

The principal lesson is that effective collaboration with AI requires explicit separation of design, observation, and conclusion. AI is valuable for structuring analysis and revealing areas worth investigating, but the student must define acceptance criteria, preserve traceability, challenge confident claims, and decide whether the available evidence is sufficient. In this assignment, disciplined human verification is therefore not a final proofreading step; it is the control that makes the AI-assisted report credible.
