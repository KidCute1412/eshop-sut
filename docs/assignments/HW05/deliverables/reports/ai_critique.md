# AI Critique

AI made the performance-testing work faster, especially when it translated the assignment into a common JMeter workflow and generated a repeatable plan structure. However, the first result also exposed its main weakness: plausible configuration is not the same as a valid execution. The generated CSV plan used explicit JMeter variable names while the CSV still contained a header row. During the first Load preflight, JMeter treated that header as credentials and produced 75 failed login samples out of 200. The failure was a test-data configuration mistake, not evidence of poor application performance. Human review preserved the failed preflight, removed the header, and reran the final scenarios successfully instead of quietly replacing the bad result.

AI also initially treated source-level lockout logic as enough to describe a defect. That would have been incomplete. A backend implementation can differ from the apparent code path because of seeded state, request handling, or test setup. The correct review step was to start with fresh local state, submit two invalid logins, then submit the valid password. The observed 401, 401, 403 sequence confirmed that the account is locked before a third failed password occurs. Only after that runtime check was a GitHub Issue packet appropriate.

The main collaboration principle is to separate proposals from evidence. AI can propose workloads, reports, thresholds, and likely causes, but JTL logs, reproducible commands, screenshots, and controlled reruns determine what can be claimed. It should also state uncertainty precisely: the Task Manager frame supports a point-in-time resource observation, not a maximum-capacity conclusion. This evidence-first workflow turns AI from an authoritative narrator into a useful, reviewable testing assistant.
