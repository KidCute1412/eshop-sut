## Partition Derivation

Each partition above is derived from FR20-R01 through FR20-R09, FR20-API01 through FR20-API03, and FR20-FORM01 through FR20-FORM04 in `requirement-analysis.md`.

Email/password presence partitions come from the documented login inputs. Credential match/mismatch and API success/rejection partitions come from the public login API contract and FR-02 login behaviour. Attempt-count and lockout partitions come from the ordered failed-attempt rule and temporary lockout rule. Lockout-message partitions come from the rule that errors must not expose detailed internal causes.

Mobile form partitions come from FR-20 mobile coverage plus FR-22 shared form requirements. Mobile UI partitions depend on an observable Expo/device/emulator runtime. API partitions depend on backend availability and disposable account setup.

## Coverage Decisions

- Normative API partitions are intended to be covered by executable API DT/BVA cases in `test-cases.md`.
- Failed-attempt threshold and lockout duration are ordered domains and should feed BVA in `boundary-value-analysis.md`.
- Mobile UI partitions are included as normative mobile coverage, but execution is `Blocked` without an Expo Go device, Android emulator, iOS simulator, or equivalent observable mobile session.
- API execution cannot prove mobile keyboard semantics, password masking, visual required markers, error placement, mobile navigation, or client-side token storage.
- Ambiguous exact messages and status bodies are not used as strict expected results.
- Client-side token storage is recorded as a coverage gap because it requires mobile runtime observation.
- Test-case coverage appears in `test-cases.md`; BVA boundaries appear in `boundary-value-analysis.md`.
