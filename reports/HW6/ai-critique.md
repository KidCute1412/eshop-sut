# HW6 - AI Critique

The AI was useful for quickly expanding the API specification into broad domain, security, and schema-oriented test ideas, but its first-pass reasoning was incomplete in several important ways. For FR01, it tried to apply the UI-only confirm-password rule directly to POST /api/register even though api_specification.md does not expose a confirmPassword field. That would have produced an unfair API oracle unless a human marked the README/API mismatch explicitly. For FR07, the AI generated ordinary add-to-cart cases but initially under-emphasized client-side price and product-name tampering: because the API body includes id, name, price, and quantity, a tester must challenge whether the backend trusts client-supplied price instead of recalculating from product data. For FR17, the AI recognized admin authorization but needed human prompting to check side effects after a user-token create attempt, not just the response status. These gaps happened because a model tends to turn a spec into field validation checklists, while security and state tests require asking what a malicious or inconsistent client could change. The main collaboration principle I learned is to use AI as a coverage amplifier, not an oracle: first make it enumerate possibilities, then force every expected result back to the source of truth, executable setup, and real evidence.
