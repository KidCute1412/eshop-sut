# AI Critique

During this performance testing assignment, I used AI to inspect the homework requirements, review the generated JMeter plans, prepare the report structure, and analyze the final JMeter logs. The AI was useful for finding gaps quickly, but it also showed why performance testing cannot be delegated blindly. Its first weakness was incompleteness during the early review: the original artifacts looked complete because the `.jmx` files existed, but the package still needed real `.jtl` logs, HTML reports, screenshots, and final measured values. A second issue was that the AI-generated CSV users were not present in the default SQLite seed data, so the login step would fail unless the database was prepared first. A third issue was endpoint-specific reasoning: the backend increments failed login attempts by 2, meaning two wrong passwords can trigger the 180-second lockout, while the generic report wording assumed a normal three-failure rule.

The AI missed these issues because it reasoned from common performance-testing templates instead of validating every assumption against the SUT source code and executable environment. After the installed Node.js and JMeter paths were confirmed, the final evidence was generated from real Load, Stress, and Spike runs. The main lesson I learned is that AI should be treated as a disciplined reviewer and drafting assistant, not as the source of truth. For performance testing, every claim must be traced back to the actual test plan, raw log, resource monitor, dashboard, or backend code.
