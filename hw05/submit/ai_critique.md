# AI Critique

During this performance testing assignment, I used AI to inspect the homework requirements, review the generated JMeter plans, and prepare the report structure. The AI was useful for finding gaps quickly, but it also showed why performance testing cannot be delegated blindly. Its first weakness was incompleteness: the original artifacts looked complete because the `.jmx` files existed, but many report sections still contained placeholders and there were no real `.jtl` logs, HTML reports, screenshots, or video evidence. A second issue was that the AI-generated CSV users were not present in the default SQLite seed data, so the login step would fail unless the database was prepared first. A third issue was endpoint-specific reasoning: the backend increments failed login attempts by 2, meaning two wrong passwords can trigger the 180-second lockout, while the generic report wording assumed a normal three-failure rule.

The AI missed these issues because it reasoned from common performance-testing templates instead of validating every assumption against the SUT source code and executable environment. It also could not create real evidence where tools were missing: this terminal had neither `jmeter` nor `node` on PATH. The main lesson I learned is that AI should be treated as a disciplined reviewer and drafting assistant, not as the source of truth. For performance testing, every claim must be traced back to the actual test plan, raw log, resource monitor, or backend code.
